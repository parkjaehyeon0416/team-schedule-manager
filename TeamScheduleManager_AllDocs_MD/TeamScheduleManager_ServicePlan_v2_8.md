# 1. ★ 출시 전략 분리 — 1차/2차 단계별 출시

## 1-1. 변경 배경

지금까지 기획서는 프리랜서(구조 C)와 팀(구조 A)을 모두 출시 시점에 지원하는 것으로 설계되어 있었어요.

하지만 실제 분석 결과 다음과 같은 문제가 있었어요:

| **문제** | **내용** |
| --- | --- |
| **타겟 메시지 모호** | "프리랜서 + 팀장 + 팀원" 모두 대상 → 누구를 위한 앱인지 불명확 |
| **개발 시간 증가** | 팀 기능(권한/공유/초대 등) 포함 시 출시까지 1~2개월 추가 소요 |
| **코드 복잡성** | 사용자 유형 분기, 권한 체크, 데이터 격리 로직 → 버그 발생 위험 |
| **마케팅 어려움** | "프리랜서 카페" + "인테리어 업체" 동시 공략 → 한쪽도 못 깊이 못 함 |

## 3-2. 기존 팀 관련 코드 처리 방침

이미 만들어둔 팀 관련 코드(팀 ID, 팀원 관계 테이블 등)는 어떻게 처리할까요?

| **대상** | **처리 방침** |
| --- | --- |
| **DB 테이블 (teams, team_users 등)** | 유지 — 데이터 구조 그대로 두되 사용 안 함 |
| **백엔드 API (TeamController 등)** | 유지 — 라우트는 등록하되 모바일에서 호출 안 함 |
| **모바일 화면 (팀 관리 등)** | 비활성화 — 햄버거 메뉴에서 숨김 처리 |
| **user_type 분기 로직** | 단순화 — 모든 사용자를 'freelancer'로 통일 |
| **웹 관리자 (operator)** | 유지 — 운영용으로 그대로 사용 |

| **💡 팀 코드를 삭제하지 않는 이유: 2차 출시 때 다시 활성화하면 되니까 굳이 삭제할 필요 없어요.** 단, 1차 출시 시 모바일 사용자에게는 보이지 않게 하면 충분해요. |
